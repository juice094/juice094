## 项目一：Clarity — 本地优先分布式 AI Agent Runtime

> Rust 原生 AI Agent 运行时，支持同一身份跨设备保持人格、记忆与社会关系一致。
> 21 crate Cargo Workspace，约 15 万行 Rust，1243 个测试，Clippy 0 warning。

### 经历 1：自研 ReAct + Plan 双模式 Agent Loop 与 MCP 工具协议

- **Situation**：现有 AI 助手处理长任务时容易遗漏步骤，且工具调用缺乏跨模型标准协议。
- **Task**：设计并实现一个可跨设备运行的 Agent 推理框架与工具协议层。
- **Action**：在 `clarity-core` 中实现 ReAct 与 Plan 双模式 Agent loop；在 `clarity-mcp` 中实现 MCP 协议，支持 stdio / SSE / WebSocket 三种传输。
- **Result**：Plan 模式显著降低长任务步骤遗漏率；MCP 工具层使 Agent 可调用本地文件、搜索、shell 等能力，且与具体 LLM provider 解耦。

### 经历 2：零外部依赖的记忆存储与混合检索

- **Situation**：AI 长期记忆需要向量检索，但外部向量数据库增加部署复杂度和隐私风险。
- **Task**：在本地优先约束下实现记忆持久化与上下文召回。
- **Action**：基于 SQLite + rusqlite 构建 `clarity-memory`，手写 `cosine_similarity` UDF 计算向量相似度，结合 BM25 全文检索与 embedding 向量搜索。
- **Result**：记忆以单文件 SQLite 存储，无需外部数据库即可支持关键词 + 语义混合召回。

### 经历 3：多入口共享同一 Agent 内核

- **Situation**：同一 Agent 需要在终端、桌面、移动端以不同形态运行。
- **Task**：实现跨平台 UI 与移动端 FFI，同时避免各端重复实现业务逻辑。
- **Action**：用 egui/eframe 构建桌面 GUI，ratatui 构建 TUI，headless 提供服务端入口；通过 UniFFI 将 Rust 核心暴露为 Android/iOS 的 cdylib/staticlib。
- **Result**：三端共享 `clarity-core`，保持 Agent 行为一致；生产代码零 unwrap/expect/panic。

## 项目二：devbase — 开发者工作空间"世界模型编译器"

> 本地优先的开发者知识库管理器，将代码库、笔记、Skill 与工作流编译为 AI 可推理的结构化上下文。
> 12 workspace crates + 主 crate，约 5.9 万行 Rust，`src/main.rs` 836 行，81 个 MCP stdio 工具。

### 经历 1：构建世界模型编译器与 81 个 MCP 工具

- **Situation**：AI 工具需要可推理的代码/笔记/工作流上下文，但云端方案存在隐私与延迟问题。
- **Task**：将本地开发者工作空间编译为结构化上下文，并通过标准协议暴露给 AI Agent。
- **Action**：用 Rust 2024 构建 devbase，集成 tree-sitter 多语言解析、SQLite WAL 关系存储、Tantivy BM25、PARA/WikiLink 知识管理；所有能力通过 MCP stdio 协议暴露为 81 个工具。
- **Result**：默认构建零 ML 运行时依赖；人类可通过 ratatui 仪表盘使用，AI 客户端可通过 `devbase mcp` 调用全部能力。

### 经历 2：SQLite + Tantivy 混合语义检索

- **Situation**：需要在无云端依赖前提下支持代码符号与笔记的关键词/语义召回。
- **Task**：设计混合检索方案，兼顾关键词精确匹配与语义相似度。
- **Action**：Tantivy 负责 BM25 全文/符号索引；SQLite BLOB 存储 embedding，注册自定义 `cosine_similarity` 标量函数计算向量相似度；混合层融合多路结果。
- **Result**：默认 feature 下无需 Candle/Ollama 即可运行关键词检索；开启 embedding feature 后可本地生成 embedding。

### 经历 3：YAML DAG 工作流引擎

- **Situation**：AI/用户需要编排多 Skill 流水线，但简单顺序执行无法满足依赖与循环需求。
- **Task**：设计并实现可配置的工作流引擎。
- **Action**：定义 Skill / Subworkflow / Parallel / Condition / Loop 5 种 step 类型，实现 YAML 解析、依赖验证、拓扑调度（Kahn 算法）、变量插值与 SQLite 持久化执行状态。
- **Result**：工作流可按依赖层级并行执行，支持条件分支与循环，执行状态可持久化与恢复。

## 项目三：syncthing-rust — Syncthing BEP 协议 Rust 实现

> 与官方 Go Syncthing 线路兼容的 P2P 文件同步守护进程。
> 9 library crate + 5 command binary，约 5.3 万行 Rust，413 passed / 6 ignored / 0 failed 测试基线。

### 经历 1：独立实现 Syncthing BEP 协议

- **Situation**：需要与 Go Syncthing 守护进程互操作的 Rust 实现，以支持本地优先的文件同步生态。
- **Task**：实现 Syncthing Block Exchange Protocol（BEP）的 Rust 版本。
- **Action**：基于 prost 完成 Hello / ClusterConfig / Index / Request / Response 等消息编解码；实现 BEP over TLS 握手；配套 `wire_compat` 集成测试验证与 Go 实现的线路格式兼容。
- **Result**：与 Go Syncthing 线路格式兼容；`cargo test --workspace` 基线 413 passed / 6 ignored / 0 failed。

### 经历 2：多路径网络发现与 NAT 穿透

- **Situation**：P2P 同步中大量设备位于 NAT 后，无法直接建立 TCP 连接。
- **Task**：实现设备发现、NAT 穿透与中继回退机制。
- **Action**：集成 UDP 本地广播、HTTPS 全球发现、STUN 公网地址探测、UPnP 端口映射与 Relay Protocol v1；当直连失败时自动 fallback 到 relay。
- **Result**：设备在复杂网络环境下可自动选择最佳连接路径，提升连接成功率。

### 经历 3：高可靠文件同步与冲突解决

- **Situation**：双向同步中并发修改容易产生冲突与数据丢失。
- **Task**：设计高可靠的块级同步链路。
- **Action**：实现 scanner / puller / index-handler / block-server 全链路块级同步；针对 Windows 句柄共享冲突实现指数退避重命名回退；基于 base/local/remote 实现文本三路合并；支持 Simple / Staggered 版本归档策略。
- **Result**：降低并发冲突与数据丢失风险；Windows release 单二进制约 16 MB，零运行时依赖。
